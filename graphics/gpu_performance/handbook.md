# GPU 架构与性能优化学习手册

> **写在前面的话**
>
> 如果你已经能写出渲染效果，但一跑就掉帧，或者画面卡顿时完全不知道该优化什么——这份手册就是为你写的。
>
> 性能优化最忌讳的是**猜测**。"我觉得是 Draw Call 太多了"、"可能是 Shader 太复杂"——这些都是猜测。正确的做法是：**先测量，找到瓶颈，再针对性优化。**
>
> 这份手册的思路是：先理解 GPU 的架构（知道它能做什么、不能做什么），再理解性能模型（知道什么决定了帧时间），最后学具体的优化技巧（知道在什么场景用什么）。
>
> 记住：**测量优先于猜测，瓶颈驱动优化。**

## 第一章 GPU 架构：与 CPU 的根本差异

### 1.1 CPU 与 GPU 的设计哲学

```
CPU：                          GPU：
┌──────────────┐              ┌──────────────────────────────┐
│  ┌────┐      │              │  ┌──┐┌──┐┌──┐┌──┐ ... ×1000 │
│  │核心│      │              │  │ALU││ALU││ALU││ALU│        │
│  │    │      │              │  └──┘└──┘└──┘└──┘            │
│  │复杂│      │              │  ┌──┐┌──┐┌──┐┌──┐            │
│  │控制│      │              │  │ALU││ALU││ALU││ALU│        │
│  │逻辑│      │              │  └──┘└──┘└──┘└──┘            │
│  └────┘      │              │  ...                          │
│  ┌────┐      │              │                              │
│  │核心│      │              │  大量简单核心                  │
│  │    │      │              │  并行处理                      │
│  │简单│      │              │                              │
│  └────┘      │              │                              │
│  少量复杂核心 │              │                              │
│  串行处理    │              │                              │
└──────────────┘              └──────────────────────────────┘

CPU 擅长：                    GPU 擅长：
- 复杂逻辑                    - 大规模并行计算
- 分支预测                    - 数据并行处理
- 低延迟                      - 高吞吐量
- 通用任务                    - 图形/矩阵运算
```

### 1.2 SIMD vs SIMT

#### SIMD（Single Instruction, Multiple Data）

CPU 的向量化指令：一条指令同时处理多个数据。

```
CPU SIMD（4 宽）：
  指令：ADD A, B, C
  执行：A[0]=B[0]+C[0], A[1]=B[1]+C[1], A[2]=B[2]+C[2], A[3]=B[3]+C[3]
  
  4 个数据同时处理
```

#### SIMT（Single Instruction, Multiple Threads）

GPU 的执行模型：一组线程（通常 32 或 64 个）执行同一条指令，但每个线程处理不同的数据。

```
GPU SIMT（32 线程一组，称为 Warp/Wavefront）：
  
  Warp 0: 32 个线程执行相同的指令
          每个线程处理不同的顶点/像素
  
  如果 32 个线程中有分支：
    if (condition) {
        // 路径 A
    } else {
        // 路径 B
    }
    
  16 个线程走路径 A，16 个走路径 B
  → 两条路径都要执行（串行化）
  → 性能损失 50%
```

**关键认知**：GPU 的分支会导致**线程发散（Thread Divergence）**，降低效率。

```glsl
// 这个 Shader 会导致线程发散
void main() {
    if (fragUV.x > 0.5) {  // 不同像素走不同分支
        color = texture(texA, fragUV);
    } else {
        color = texture(texB, fragUV);
    }
}

// 优化：用 mix 代替 if
void main() {
    vec4 colorA = texture(texA, fragUV);
    vec4 colorB = texture(texB, fragUV);
    color = mix(colorA, colorB, step(0.5, fragUV.x));
}
```

### 1.3 GPU 的内存层级

```
GPU 内存层级（从快到慢）：

┌─────────────────────────────────────────┐
│ 寄存器（Register）                       │  ← 最快，每个线程私有
│ 延迟：< 1 周期                           │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│ 共享内存 / 本地数据共享（Shared Memory） │  ← 同一工作组共享
│ 延迟：~20 周期                           │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│ L1 缓存                                │  ← 每个 SM 私有
│ 延迟：~30 周期                           │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│ L2 缓存                                │  ← 所有 SM 共享
│ 延迟：~200 周期                          │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│ 显存（VRAM / GDDR / HBM）              │  ← 最慢，容量最大
│ 延迟：~400 周期                          │
└─────────────────────────────────────────┘
```

**优化原则**：
- 尽量复用数据，利用缓存
- 减少显存访问（带宽是瓶颈）
- 纹理用压缩格式，减少带宽

### 1.4 CPU-GPU 通信开销

CPU 和 GPU 通过 PCIe 总线通信，带宽有限：

```
CPU 内存 ←──PCIe 总线──→ GPU 显存
         带宽：~32 GB/s（PCIe 4.0 x16）
         延迟：~1 微秒
```

**通信开销来源**：
1. **Draw Call 提交**：CPU 每次提交 Draw Call，都要通过驱动发送给 GPU
2. **纹理/缓冲区上传**：从 CPU 内存复制到 GPU 显存
3. **回读**：从 GPU 显存读回 CPU（非常慢，尽量避免）

```
Draw Call 提交流程：
  CPU                    GPU
   │                      │
   │──Draw Call 1────────→│
   │                      │──执行
   │──Draw Call 2────────→│
   │                      │──执行
   │──Draw Call 3────────→│
   │                      │──执行
   │                      │
   
  每个 Draw Call 都有开销（~5-10 微秒）
  10000 个 Draw Call = 50-100 ms（太多！）
```

### 1.5 如何判断 CPU-GPU 通信是不是瓶颈

**检查清单**：

- [ ] Draw Call 数量 > 2000？
- [ ] 每帧有大量纹理/缓冲区上传？
- [ ] 有从 GPU 回读数据的操作（如 `glReadPixels`、`vkMapMemory` 读回）？
- [ ] CPU 帧时间 >> GPU 帧时间？（CPU bound）

**如果是瓶颈**：
- 合批、实例化渲染
- 减少每帧的资源上传
- 避免 GPU 回读

## 第二章 GPU 性能模型：什么决定了帧时间

### 2.1 帧时间的组成

```
一帧的总时间 = CPU 时间 + GPU 时间 + 同步等待

CPU 时间：
  - 场景遍历、剔除
  - Draw Call 提交
  - 物理、动画、AI

GPU 时间：
  - 顶点处理
  - 光栅化
  - 片元处理
  - 输出合并

同步等待：
  - CPU 等 GPU（GPU bound）
  - GPU 等 CPU（CPU bound）
  - GPU 等 GPU（资源依赖）
```

### 2.2 GPU 的两大瓶颈类型

#### 顶点瓶颈（Vertex Bound）

GPU 忙于处理顶点（顶点着色器）。

```
特征：
  - 顶点数很多（高模、大量实例）
  - 顶点着色器复杂
  - GPU 的顶点处理单元满载
```

#### 片元瓶颈（Fragment/Pixel Bound）

GPU 忙于处理片元（片元着色器）。

```
特征：
  - 过度绘制严重
  - 片元着色器复杂（多纹理、多光照）
  - 分辨率高
  - GPU 的片元处理单元满载
```

#### 带宽瓶颈（Bandwidth Bound）

GPU 忙于读写显存。

```
特征：
  - 大量纹理采样
  - 多个渲染目标（MRT）
  - 高分辨率 + 高精度格式
  - 显存带宽饱和
```

### 2.3 性能模型公式

```
GPU 帧时间 ≈ max(
    顶点数 × 顶点处理时间,
    片元数 × 片元处理时间,
    数据量 / 带宽
) + 同步开销
```

**关键认知**：GPU 的性能取决于**最慢的那个阶段**。优化其他阶段不会有帮助。

### 2.4 如何判断瓶颈类型

**检查清单**：

#### 判断是否 Vertex Bound

- [ ] 降低分辨率后，帧率没有提升？
- [ ] 减少模型面数后，帧率明显提升？
- [ ] 顶点着色器有大量计算（骨骼蒙皮、 morph target）？

**如果是 Vertex Bound**：
- LOD（远处用低模）
- 视锥剔除、遮挡剔除
- 简化顶点着色器
- 用 GPU 实例化减少顶点数据

#### 判断是否 Fragment Bound

- [ ] 降低分辨率后，帧率明显提升？
- [ ] 减少过度绘制后，帧率提升？
- [ ] 片元着色器复杂（多纹理、多光照、复杂数学）？

**如果是 Fragment Bound**：
- 降低分辨率
- 减少过度绘制（按深度排序、Early-Z）
- 简化片元着色器
- 用延迟渲染减少光照计算

#### 判断是否 Bandwidth Bound

- [ ] 使用压缩纹理后，帧率提升？
- [ ] 减少渲染目标数量后，帧率提升？
- [ ] 降低纹理分辨率后，帧率提升？

**如果是 Bandwidth Bound**：
- 用压缩纹理（BC/ASTC/ETC2）
- 减少渲染目标（MRT）数量
- 降低纹理分辨率
- 用 Tile-Based 渲染（移动端）

### 2.5 性能优化的优先级

```
1. 先确定瓶颈类型（Vertex / Fragment / Bandwidth / CPU）
2. 针对瓶颈优化
3. 不要优化非瓶颈的部分（浪费时间）
```

```
错误的优化思路：
  "我觉得 Draw Call 太多了，合批一下"
  → 但实际瓶颈是片元着色器太复杂
  → 合批后帧率没有提升
  → 浪费时间

正确的优化思路：
  1. 测量：Draw Call = 500，GPU 时间 = 16ms
  2. 分析：降低分辨率后 GPU 时间 = 8ms → Fragment Bound
  3. 优化：简化片元着色器 / 减少过度绘制
  4. 验证：GPU 时间 = 6ms → 优化成功
```

## 第三章 Draw Call 与合批优化

### 3.1 Draw Call 的开销

每个 Draw Call 都有固定开销：

```
Draw Call 开销：
  CPU 侧：
    - 设置渲染状态（Pipeline、Descriptor Set）
    - 绑定顶点/索引缓冲区
    - 提交命令到驱动
    - 驱动验证、转换
    
  GPU 侧：
    - 切换渲染状态
    - 加载新的 Shader/纹理
    
  典型开销：~5-10 微秒 / Draw Call
```

```
10000 个 Draw Call × 5 微秒 = 50 ms
→ 60 FPS 需要 16.67 ms / 帧
→ 50 ms >> 16.67 ms
→ 严重掉帧
```

### 3.2 合批（Batching）

#### 静态合批（Static Batching）

把多个静态物体（不移动的）合并成一个大网格。

```
合批前：
  Draw Call 1: 画树 A
  Draw Call 2: 画树 B
  Draw Call 3: 画树 C
  
合批后：
  Draw Call 1: 画树 A + B + C（合并成一个大网格）
```

**优点**：
- 减少 Draw Call
- 不增加顶点数

**缺点**：
- 增加内存占用（合并后的网格要存一份）
- 只能用于静态物体

#### 动态合批（Dynamic Batching）

每帧动态合并小的物体。

**限制**：
- 只能合并使用相同材质的物体
- 顶点数有限制（通常 < 300 个顶点）
- 有 CPU 开销（每帧要合并）

### 3.3 GPU 实例化（Instancing）

用一次 Draw Call 画多个相同的物体，每个实例可以有不同的参数。

```
实例化渲染：
  Draw Call 1: 画 1000 棵树
    - 每个树的位置、旋转、缩放不同
    - 通过实例缓冲区传入
```

```cpp
// Vulkan 实例化
struct InstanceData {
    vec4 position;    // 位置
    vec4 rotation;    // 旋转（四元数）
    vec4 scale;       // 缩放
    vec4 color;       // 颜色
};

// 创建实例缓冲区
VkBuffer instanceBuffer;
vkCreateBuffer(device, &bufferInfo, nullptr, &instanceBuffer);

// 绑定实例缓冲区
vkCmdBindVertexBuffers(commandBuffer, 1, 1, &instanceBuffer, offsets);

// 实例化绘制
vkCmdDraw(commandBuffer, vertexCount, instanceCount, 0, 0);
//                                 ↑ 实例数量
```

```glsl
// 顶点着色器
layout(location = 3) in vec4 instancePosition;
layout(location = 4) in vec4 instanceRotation;
layout(location = 5) in vec4 instanceScale;

void main() {
    // 用实例数据变换顶点
    vec3 pos = position * instanceScale.xyz;
    pos = rotate(pos, instanceRotation);
    pos += instancePosition.xyz;
    
    gl_Position = mvp * vec4(pos, 1.0);
}
```

**优点**：
- 极大减少 Draw Call
- 适合大量相同物体（草、树、粒子）
- 每个实例可以有不同参数

**缺点**：
- 只能用于相同网格
- 需要支持实例化的 Shader

### 3.4 间接绘制（Indirect Draw）

把绘制参数放在 GPU 显存中，GPU 自己读取参数，减少 CPU 提交开销。

```
传统绘制：
  CPU 每个 Draw Call 都要提交参数
  
间接绘制：
  CPU 一次性提交所有参数到 GPU
  GPU 自己读取参数，逐个绘制
```

```cpp
// Vulkan 间接绘制
struct VkDrawIndirectCommand {
    uint32_t vertexCount;
    uint32_t instanceCount;
    uint32_t firstVertex;
    uint32_t firstInstance;
};

// 创建间接缓冲区
VkBuffer indirectBuffer;
// 填充命令到 indirectBuffer

// 间接绘制
vkCmdDrawIndirect(commandBuffer, indirectBuffer, 
                  commandCount, sizeof(VkDrawIndirectCommand));
```

**优点**：
- 减少 CPU 开销
- 可以和 GPU 剔除结合（剔除后的物体直接跳过）

### 3.5 如何判断 Draw Call 是不是瓶颈

**检查清单**：

- [ ] Draw Call 数量 > 1000？
- [ ] CPU 帧时间 > GPU 帧时间？
- [ ] 合批或实例化后，CPU 帧时间明显下降？

**如果是瓶颈**：
- 合批（静态/动态）
- GPU 实例化
- 间接绘制
- 减少材质切换（按材质排序）

## 第四章 剔除与 LOD

### 4.1 视锥体剔除（Frustum Culling）

#### 原理

检查物体的包围盒/包围球是否在摄像机的视锥体内。不在的直接跳过。

```
俯视图：

  摄像机 →
  
   \         /
    \  △   /   ← 在视锥体内，保留
     \    /
      \  /
       \/
       
  ● ← 不在视锥体内，剔除
```

#### 实现

```cpp
// 球体 vs 视锥体检测
bool isSphereInFrustum(const BoundingSphere& sphere, const Frustum& frustum) {
    for (int i = 0; i < 6; i++) {
        float distance = dot(frustum.planes[i].normal, sphere.center) + frustum.planes[i].distance;
        if (distance < -sphere.radius) {
            return false;  // 球体完全在平面外
        }
    }
    return true;  // 球体和视锥体相交或完全在内
}
```

#### 优化：层次包围盒（BVH）

```
场景树：
  Root
  ├── Node A (包围盒)
  │   ├── 物体 1
  │   └── 物体 2
  └── Node B (包围盒)
      ├── 物体 3
      └── 物体 4

剔除时：
  1. 检查 Root → 在视锥体内
  2. 检查 Node A → 不在视锥体内 → 跳过整个子树
  3. 检查 Node B → 在视锥体内
  4. 检查物体 3、4 → 保留
```

### 4.2 遮挡剔除（Occlusion Culling）

#### 原理

如果一个物体完全被另一个物体挡住，就不画它。

```
俯视图：

  摄像机 →
  
    ████ ← 大墙
    ████
    
    ░░░░ ← 被墙完全挡住，剔除
    ░░░░
```

#### 实现方法

##### 硬件遮挡查询（Hardware Occlusion Query）

```cpp
// 创建遮挡查询对象
VkQueryPool queryPool;
vkCreateQueryPool(device, &queryPoolInfo, nullptr, &queryPool);

// 渲染简化版物体（如包围盒）
vkCmdBeginQuery(commandBuffer, queryPool, queryIndex, 0);
drawBoundingBox(object);
vkCmdEndQuery(commandBuffer, queryPool, queryIndex);

// 查询结果
uint64_t samplesPassed;
vkGetQueryPoolResults(device, queryPool, queryIndex, 1, 
                      sizeof(samplesPassed), &samplesPassed, 0, 0);

if (samplesPassed == 0) {
    // 完全被遮挡，不画
} else {
    // 可见，画完整模型
}
```

##### 软件遮挡剔除（Software Occlusion Culling）

```
预计算：
  1. 把场景分成网格（Grid）
  2. 对每个网格单元，计算从哪些方向可以看到它
  3. 运行时，根据摄像机位置，判断哪些网格单元可见
```

### 4.3 LOD（Level of Detail）

#### 原理

远处的物体用小模型，近处的物体用大模型。

```
LOD 0: 10000 面（近距离）
LOD 1: 2000 面（中距离）
LOD 2: 500 面（远距离）
LOD 3: 100 面（超远距离）
```

#### 切换策略

```cpp
float distance = length(objectPosition - cameraPosition);

if (distance < 10.0f) {
    drawLOD(0);  // 高精度
} else if (distance < 30.0f) {
    drawLOD(1);  // 中精度
} else if (distance < 100.0f) {
    drawLOD(2);  // 低精度
} else {
    drawLOD(3);  // 最低精度（或 Billboard）
}
```

#### 平滑过渡

LOD 切换时会有明显的"跳变"，可以用**morphing**平滑过渡：

```
LOD 0 → LOD 1 过渡：
  在距离 9~11 米范围内，混合 LOD 0 和 LOD 1
  
  blendFactor = (distance - 9.0) / 2.0
  finalMesh = lerp(LOD0, LOD1, blendFactor)
```

### 4.4 如何判断剔除和 LOD 是不是需要优化

**检查清单**：

- [ ] 场景中有很多不可见的物体（被墙挡住、在视锥体外）？
- [ ] 远处有很多高精度模型？
- [ ] 添加视锥剔除后，Draw Call 明显减少？
- [ ] 添加 LOD 后，顶点数明显减少？

**如果需要优化**：
- 实现视锥剔除
- 实现遮挡剔除（室内场景特别有效）
- 为所有模型制作 LOD
- 用 GPU 剔除（Compute Shader）

## 第五章 过度绘制与带宽优化

### 5.1 过度绘制（Overdraw）

#### 定义

同一个像素被多个三角形覆盖，导致多次绘制。

```
场景：一堵墙前面有一片树叶

  摄像机 → 🍃 → 🧱
  
  像素 A 被画了两次：
    第一次：画墙
    第二次：画树叶（覆盖在墙上）
    
  过度绘制 = 2
```

#### 危害

- 浪费 GPU 计算资源（片元着色器执行多次）
- 浪费带宽（多次读写帧缓冲区）

#### 测量过度绘制

```
过度绘制可视化：
  对每个像素，记录它被绘制了多少次
  用颜色表示：
    绿色 = 1 次（理想）
    黄色 = 2~3 次
    红色 = 4+ 次（严重）
```

### 5.2 减少过度绘制

#### 方法一：按深度排序（前向渲染）

```
从近到远绘制：
  1. 画近处的物体
  2. 画远处的物体
  
  好处：
    远处的物体被近处的遮挡
    深度测试会丢弃被遮挡的片元
    减少片元着色器的执行
```

#### 方法二：延迟渲染

```
延迟渲染：
  1. 几何 Pass：写 G-Buffer（每个像素只写一次）
  2. 光照 Pass：读取 G-Buffer，计算光照
  
  好处：
    光照计算和几何复杂度解耦
    减少过度绘制（每个像素只计算一次光照）
```

#### 方法三：遮挡剔除

```
不画完全被遮挡的物体
→ 直接减少过度绘制
```

#### 方法四：Alpha to Coverage

```
用 MSAA 的 Alpha to Coverage：
  透明物体的边缘用 Alpha 测试
  减少透明物体的过度绘制
  
  适合：植被、铁丝网
```

### 5.3 带宽优化

#### 压缩纹理

```
未压缩纹理（RGBA8）：
  4 字节 / 像素
  1024×1024 = 4 MB
  
压缩纹理（BC3 / ASTC）：
  1 字节 / 像素（4:1 压缩）
  1024×1024 = 1 MB
  
  带宽减少 75%
```

| 平台 | 推荐格式 |
|------|----------|
| PC | BC1-BC7 |
| iOS | ASTC |
| Android | ETC2 / ASTC |

#### 减少渲染目标切换

```
错误的做法：
  Render Target A → 渲染
  Render Target B → 渲染
  Render Target A → 渲染  ← 切换回 A，带宽浪费

正确的做法：
  把所有需要写入 A 的操作合并
  Render Target A → 渲染所有
  Render Target B → 渲染所有
```

#### 降低精度

```
HDR 纹理：
  R16G16B16A16_SFLOAT = 8 字节 / 像素
  
  如果不需要高精度：
  R11G11B10_UFLOAT = 4 字节 / 像素
  带宽减少 50%
```

### 5.4 Early-Z 与 Hi-Z

#### Early-Z

在片元着色器之前做深度测试，提前丢弃被遮挡的片元。

```
正常流程：
  光栅化 → 片元着色器 → 深度测试 → 写入
  
Early-Z 流程：
  光栅化 → 深度测试（提前） → 片元着色器 → 写入
  
  好处：被遮挡的片元不需要执行片元着色器
```

#### Early-Z 失效场景

| 场景 | 原因 |
|------|------|
| 片元着色器中写入深度 | GPU 无法提前知道深度值 |
| 透明物体 | 需要混合，不能简单丢弃 |
| Alpha Test | 片元着色器中 `discard` |
| 深度写入关闭 | 无法更新深度缓冲区 |

#### Hi-Z（Hierarchical Z-Buffer）

用多层深度缓冲区，快速判断一个 Tile 是否完全被遮挡。

```
Hi-Z 金字塔：
  Level 0: 全分辨率深度图
  Level 1: 半分辨率（取 2×2 块的最大深度）
  Level 2: 1/4 分辨率
  ...
  
  遮挡查询时：
    从高层开始检查
    如果整个 Tile 被遮挡，直接跳过
    否则，用下一层继续检查
```

### 5.5 如何判断过度绘制和带宽是不是瓶颈

**检查清单**：

#### 过度绘制

- [ ] 过度绘制可视化显示大量红色区域？
- [ ] 按深度排序后，帧率提升？
- [ ] 减少透明物体叠加后，帧率提升？

#### 带宽

- [ ] 使用压缩纹理后，帧率提升？
- [ ] 降低纹理分辨率后，帧率提升？
- [ ] 减少渲染目标数量后，帧率提升？
- [ ] 降低精度（如 R16 → R11）后，帧率提升？

**如果是瓶颈**：
- 减少过度绘制（排序、剔除、延迟渲染）
- 用压缩纹理
- 减少渲染目标
- 降低精度

## 第六章 移动端 vs PC 端架构差异

### 6.1 两种架构

#### 立即模式渲染（Immediate Mode Rendering）—— PC / 主机

```
立即模式：
  CPU 提交 Draw Call → GPU 立即执行 → 写入显存
  
  特点：
    - 每个 Draw Call 立即开始执行
    - 需要大量显存带宽
    - 适合高带宽的 PC / 主机
```

#### Tile-Based 延迟渲染（TBDR）—— 移动端

```
TBDR：
  1. 分块：把屏幕分成小块（Tile），如 16×16 像素
  2. 几何处理：对所有 Draw Call，判断每个 Tile 需要哪些三角形
  3. 片元处理：对每个 Tile，独立执行片元着色器
  
  特点：
    - 利用缓存局部性
    - 减少显存带宽
    - 适合带宽受限的移动端
```

```
立即模式：                    TBDR：
                              
  Draw Call 1 → 执行          所有 Draw Call → 分块
  Draw Call 2 → 执行          Tile 0 → 执行
  Draw Call 3 → 执行          Tile 1 → 执行
  ...                         ...
  
  每个 Draw Call 都要读写显存   每个 Tile 在片上缓存完成
```

### 6.2 移动端的特殊注意事项

#### 带宽是最大瓶颈

```
PC 显存带宽：  500~1000 GB/s
移动端带宽：   10~50 GB/s

差距：20~100 倍
```

**优化策略**：
- 用 TBDR 架构（利用片上缓存）
- 用压缩纹理（ASTC / ETC2）
- 降低分辨率
- 减少渲染目标

#### 发热与降频

```
移动端 GPU 会发热
长时间高负载 → 降频 → 帧率下降

解决方案：
  - 控制 GPU 负载（不要长时间满载）
  - 动态调整画质（根据温度）
  - 用更激进的优化（LOD、剔除）
```

#### 内存限制

```
PC 显存：  4~24 GB
移动端：   2~8 GB（和系统共享）

解决方案：
  - 压缩纹理
  - 减少纹理分辨率
  - 流式加载（按需加载资源）
```

### 6.3 移动端优化清单

**检查清单**：

- [ ] 使用压缩纹理（ASTC / ETC2）？
- [ ] 分辨率是否合理（1080p 或更低）？
- [ ] 渲染目标数量是否最少？
- [ ] 是否利用了 TBDR 架构（避免不必要的 Load/Store）？
- [ ] 是否控制了 Draw Call（< 500）？
- [ ] 是否用了 LOD 和剔除？

**移动端推荐配置**：

| 纹理总大小 | < 500 MB |
| 渲染目标 | 2~3 个 |
| 分辨率 | 1080p 或 720p |

**检查清单**：

## 第七章 常见性能陷阱与诊断思路

### 7.1 陷阱一：过多的 Draw Call

**症状**：
- CPU 帧时间高
- GPU 帧时间低
- 增加合批后帧率提升

**诊断思路**：
1. 统计 Draw Call 数量
2. 检查 CPU 帧时间 vs GPU 帧时间
3. 如果 CPU >> GPU，且 Draw Call 多 → Draw Call 瓶颈

**解决方案**：
- 合批（静态/动态）
- GPU 实例化
- 间接绘制
- 按材质排序，减少状态切换

### 7.2 陷阱二：过度绘制

**症状**：
- GPU 帧时间高
- 降低分辨率后帧率提升
- 过度绘制可视化显示大量红色

**诊断思路**：
1. 检查 GPU 帧时间
2. 降低分辨率，看帧率是否提升
3. 如果提升 → Fragment Bound
4. 用过度绘制可视化确认

**解决方案**：
- 按深度排序（前向渲染）
- 延迟渲染
- 遮挡剔除
- 减少透明物体叠加

### 7.3 陷阱三：复杂的片元着色器

**症状**：
- GPU 帧时间高
- 简化 Shader 后帧率提升
- 片元处理单元满载

**诊断思路**：
1. 检查 GPU 帧时间
2. 简化片元着色器（减少纹理、减少计算）
3. 如果帧率提升 → Shader 瓶颈

**解决方案**：
- 简化 Shader（减少纹理采样、减少数学运算）
- 用 LOD（远处用简化版 Shader）
- 预计算（把复杂计算放到 CPU 或预计算纹理）

### 7.4 陷阱四：带宽瓶颈

**症状**：
- GPU 帧时间高
- 使用压缩纹理后帧率提升
- 降低纹理分辨率后帧率提升

**诊断思路**：
1. 检查 GPU 帧时间
2. 使用压缩纹理，看帧率是否提升
3. 如果提升 → 带宽瓶颈

**解决方案**：
- 用压缩纹理
- 减少渲染目标
- 降低精度
- 用 Tile-Based 渲染（移动端）

### 7.5 陷阱五：CPU-GPU 同步

**症状**：
- 帧时间波动大
- 有时卡顿
- CPU 和 GPU 都在等

**诊断思路**：
1. 检查是否有 GPU 回读（`glReadPixels`、`vkMapMemory` 读回）
2. 检查是否有过多的资源上传
3. 检查 CPU 和 GPU 的帧时间是否接近

**解决方案**：
- 避免 GPU 回读
- 用双缓冲/三缓冲（减少同步等待）
- 异步上传资源

### 7.6 陷阱六：过多的透明物体

**症状**：
- GPU 帧时间高
- 过度绘制严重
- 按深度排序后帧率提升

**诊断思路**：
1. 检查透明物体数量
2. 检查过度绘制
3. 如果透明物体多且过度绘制严重 → 透明物体瓶颈

**解决方案**：
- 按深度排序（从远到近）
- 用 Alpha to Coverage（代替 Alpha 混合）
- 减少透明物体叠加
- 用 Order Independent Transparency（OIT）

### 7.7 通用诊断流程

```
1. 测量帧时间
   - CPU 帧时间
   - GPU 帧时间
   
2. 判断瓶颈类型
   - CPU >> GPU → CPU Bound（Draw Call、场景遍历）
   - GPU >> CPU → GPU Bound（Vertex / Fragment / Bandwidth）
   - CPU ≈ GPU → 平衡或同步等待
   
3. 针对瓶颈优化
   - CPU Bound：合批、实例化、剔除
   - Vertex Bound：LOD、剔除、简化顶点 Shader
   - Fragment Bound：减少过度绘制、简化片元 Shader
   - Bandwidth Bound：压缩纹理、减少 RT、降低精度
   
4. 验证优化效果
   - 重新测量帧时间
   - 确认瓶颈是否解决
   - 如果没有，继续分析
```

> **最后的话**
>
> 性能优化是一门**实证科学**。不要猜测，要测量。不要盲目优化，要找到瓶颈。
>
> 记住三个原则：
> 1. **测量优先于猜测**：用工具测量，不要凭直觉
> 2. **瓶颈驱动优化**：只优化瓶颈，不要优化非瓶颈
> 3. **验证优化效果**：每次优化后重新测量，确认效果
>
> 最后，性能优化是一个持续的过程。随着项目的发展，瓶颈会变化。保持测量的习惯，持续优化。
