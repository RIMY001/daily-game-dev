\# W1 交汇：控制块 × 资源生命周期



\## 1. 解决什么问题



多个所有者共享同一资源，由"最后一个离开的人"负责销毁。



\## 2. 结构 + 数据流



控制块是资源的\*\*户口本\*\*：谁活着、谁能删、何时删。`shared\_ptr` 持有两个指针：`T\* ptr\_` 与 `ControlBlock\* cb\_`。



拷贝 `++shared`；构造 weak `++weak`。资源先死，块后死，中间窗口是 weak 的安全区。



\## 3. 当周知识



\- C++：RAII、placement new、union / 共用存储、删除器函数指针、lambda 隐转函数指针、对齐`alignas`、模板、reinterpret\_cast

\- 算法 / 数据结构：引用计数（RC）、分离元数据（元数据与实体解耦）

\- 系统（OS / 网络 / 图形）：内存分配粒度、内存局部性（make\_shared 一次分配优势）、句柄（Handle）生命周期管理、延迟释放



\## 4. 换一种设计



若去掉 `weak\_count`，资源与块同时销毁，`weak\_ptr::lock()` 失去立足点，必然悬空。若改用 GC（如 Java），则失去确定性析构——文件句柄、GPU 资源无法及时释放。



\## 5. 我会怎么改



当前版本用函数指针`void(\*)(T\*)`做删除器，只能支持无捕获 lambda；

\*\*改进点：把删除器升级成`std::function<void(T\*)>`类型擦除删除器\*\*。

收益：支持带捕获的自定义删除器（比如捕获分配器、引擎资源管理器、文件句柄），对齐 std::shared\_ptr 能力；代价是一点点内存开销、间接调用开销，适合引擎资源系统对接。

\## 6. 三道面试追问



1\. 引擎能不能照搬这套思路做弱句柄？> \*\*弱句柄的思想完全可以搬，但是释放策略要交给资源管理器，而不是像 shared\_ptr 一样硬编码在计数判断里\*\*。

2\. 单次分配下大对象会拖住控制块内存，怎么权衡？小对象用make\_shared;大对象用new+shared\_ptr

3\. 控制块与引擎资源句柄（handle）是不是同一件事？控制块 = 带引用计数的 handle。
